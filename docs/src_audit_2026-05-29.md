# vkmEngine deep-dive audit — architecture, genericity, performance, organization

**Date:** 2026-05-29
**Scope:** all of `src/` (~288 files, ~31.5k LOC), read in full via parallel per-subsystem deep dives.
**Branch:** `vkm/dev/shading`

This document answers four questions:
1. Where are specific/hardcoded implementations that should have been generic?
2. What architectural choices have issues?
3. How can the renderer be made faster (currently ~300 FPS at max settings even on a small scene)?
4. Is it time to reorganize files?

---

## First: three stale "facts" corrected by the audit

Several long-standing assumptions are wrong in the current code. They change the framing, so they come first:

1. **The engine is *not* a singleton.** There is no `Engine::get()`. `Engine` is stack-constructed, non-copyable, and injects state into systems via `FrameContext` ([core/system.h:58](../src/engine/core/system.h#L58)). Only a stale comment in `render_graph_context.h:35` still says otherwise. This is *good* design — do not revert it to a singleton.
2. **There is no 64-type `uint64_t` component bitmask.** `Scene` is fully type-erased: `std::vector<std::unique_ptr<ISparseSet>>` indexed by `typeId<T>()` ([ecs/scene.h:322](../src/engine/ecs/scene.h#L322)). No 64-type ceiling exists.
3. **Events and serialization are already generic.** Events are a typed templated dispatcher keyed on `typeId<EventT>()`, not `std::any` + FNV string keys. Serialization has a real compile-time reflection layer (`io/reflect.h` + `VKM_REFLECT`), not hand-written-per-type. Most components serialize as one-liners.

Net: the codebase is **more mature than expected**. Genericity gaps are narrow and specific; engine/backend layering is genuinely clean (a repo-wide grep for GL types in `src/engine` returns a single *comment*).

## Q3 — Renderer performance (the headline)

**Diagnosis: fixed-cost-per-frame bound, not geometry bound.** ~300 FPS = ~3.3 ms/frame. With a small scene, geometry is nearly free, so that 3.3 ms is almost entirely *scene-size-independent overhead*: two synchronous GPU readbacks that stall the render thread every frame, full per-pass profiling instrumentation, and ~20 always-on full-resolution passes. That is why shrinking the scene doesn't help.

Already done well (do **not** "fix" these): GL state is deduped/cached, instancing/batching is real, the render graph is **not** rebuilt per frame, UBOs are change-gated, vsync is off and the frame limiter is disabled (so 300 is real work, not an artificial cap).

### Tier 0 — measure & near-free wins (do first; likely the bulk of the gain)

**0a. Re-benchmark with `VKM_PROFILER=OFF` and `TRACY_ENABLE=OFF`.**
Current build is `RelWithDebInfo` with both `TRACY_ENABLE=ON` and `VKM_PROFILER=ON` (verified in `build/CMakeCache.txt`). Every pass is instrumented by **two** independent GPU timer systems — the backend `GL_TIME_ELAPSED` query ring ([gl_backend.cpp:55-93](../src/backend/opengl/core/gl_backend.cpp#L55-L93)) **and** a Tracy `glQueryCounter` GPU zone at the top of all 20 passes — plus `TracyGpuCollect` each frame. That is ~80+ query GL calls + 40 Tracy zones/frame on sub-100µs passes. Cheapest experiment; establishes the true ceiling. Then keep at most one timer system, gated behind "profiler panel open."

**0b. Drop `GLHiZPass` from the pipeline (or PBO-defer its readback).**
[gl_hiz_pass.cpp:106-108](../src/backend/opengl/pass/gl_hiz_pass.cpp#L106-L108) does a synchronous `glReadPixels` every frame — a full GPU pipeline flush/stall — to produce occlusion data that **has no consumer yet** ([engine_app.cpp:175](../src/engine_app/engine_app.cpp#L175) comments "No consumer yet (#20)") while [engine_app.cpp:203](../src/engine_app/engine_app.cpp#L203) keeps it in the live pipeline. Remove `"GLHiZPass"` from the pipeline list until something reads it; when wired up, use a double-buffered PBO so the CPU reads frame N-1 without blocking. **Highest impact, lowest risk change in the audit.**

**0c. Gate/defer the auto-exposure readback.**
[gl_auto_exposure.h:112-119](../src/backend/opengl/resource/gl_auto_exposure.h#L112-L119) does a blocking `glGetTexImage` **every frame** to feed the editor's EV readout (its own comment says it's "only worth paying for the editor's adapted-EV readout, not the runtime path"). Gate behind "exposure panel visible," or read every N frames via PBO. The runtime never needs it.

> 0b + 0c are two full CPU↔GPU serialization points per frame on the render thread. With 0a's instrumentation, these three account for a large chunk of the 3.3 ms and are all scene-size-independent — exactly matching the symptom.

### Tier 1 — structural per-frame CPU overhead

- **1a. "Scene unchanged" short-circuit.** The whole 20-pass pipeline executes every frame regardless of change ([render_graph.cpp:286](../src/engine/system/render/render_graph.cpp#L286)); only `GLShadowPass` has a skip guard. Compute a scene+camera+env signature (shadow pass shows the pattern) and re-present the last composite when static. The editor material-preview change-detection (commit 93ca764) is the mechanism to generalize.
- **1b. `parallelFor` fast-path for small N.** [thread_pool.h:96-109](../src/engine/platform/threading/thread_pool.h#L96-L109) allocates a `std::vector` of heap-allocating `std::function` tasks and does a full threadpool round-trip (mutex + `notify_all` + wait) every call — invoked per frame by visibility culling and per depth-bucket by transform resolve. On a small scene the dispatch costs more than the work. Add `if (count < threshold) { serial; return; }`.
- **1c. Change-detect the instance/shadow batcher + camera/lights UBO uploads.** [gl_view.cpp:179](../src/backend/opengl/core/gl_view.cpp#L179) rebuilds both batchers and re-uploads the full instance matrix buffer every frame, even on a static scene. Gate `build()` on a content hash/dirty flag (the resource-table sync just above already does this).
- **1d. Cache `RenderView` gathers.** [render_view.cpp:135](../src/engine/system/render/render_view.cpp#L135) re-gathers and re-sorts the whole scene every frame; the shadow-caster gather is O(*all* meshes), not O(visible). Rebuild only on a scene/transform-dirty signal.

### Tier 2 — GPU bandwidth (scales with *resolution* — the "max settings" complaint)

- **2a. Collapse repeated full-res MSAA resolves.** SSR and LensFlare write back into MSAA `SceneHDR`, forcing a fresh full-res 4×MSAA RGBA16F→1× resolve blit at each subsequent reader (TAA/Bloom/Exposure/Composite) — ~4-6 resolves/frame at max. Run SSR/LensFlare in already-resolved single-sample space so there is exactly one resolve. **Strongly consider dropping MSAA entirely** — TAA already provides edge AA, making 4×MSAA on an RGBA16F target largely redundant (removes the resolves *and* halves SceneHDR bandwidth).
- **2b. Run SSR / DoF / Motion Blur / Lens Flare at half (or quarter) resolution.** Bloom and GTAO are already half-res (good); these four run at full-res RGBA16F. They are low-frequency effects that look near-identical at half-res with a cheap upsample. Biggest "high-res at max settings" win; invisible at small scene sizes today.
- **2c. Skip the unconditional overlay clear+resolve.** [gl_composite_pass.cpp:231](../src/backend/opengl/pass/gl_composite_pass.cpp#L231) always does a second full-res MSAA resolve of the debug-overlay attachment, even though overlays are off in normal play. Track an "overlay dirty" flag and skip when nothing drew to it.

### Tier 3 — per-draw CPU & state churn (grows with material variety)

- **Uniform-location cache allocates a `std::string` per lookup** ([gl_shader_base.cpp:135-159](../modules/vkmGL/src/shader/gl_shader_base.cpp#L135-L159)) — `unordered_map<std::string,int>` with `const char*` lookups constructs+hashes a temporary every call, dozens of times/frame. Use heterogeneous lookup (`is_transparent`), or move the ~15 frame-wide PBR uniforms into a per-frame UBO so they aren't re-pushed on every shader-variant switch.
- **No redundant texture-bind suppression** ([gl_material.cpp:137-147](../src/backend/opengl/resource/gl_material.cpp#L137-L147)) — re-binds up to 11 texture slots per material per pass every frame (camera/lights UBOs `memcmp`-skip, but textures don't). Add a per-slot `lastBoundTex` cache in the context.
- **Each fullscreen pass owns its own `ScreenTriangle` VAO** (~12 of them; its docstring claims they're shared). Make it one static VAO bound once.
- **`OcclusionCuller` copies the entire Hi-Z pyramid per entity under a mutex** ([occlusion_culler.h:46](../src/engine/system/visibility/culling/occlusion_culler.h#L46)) — if Hi-Z is kept, snapshot it once per frame, not per `isVisible` call.

## Q1 — Specific-where-it-should-be-generic

Strongest pattern: **the editor + serializer have ~6 parallel hardcoded per-component switch-ladders** that must be edited in lockstep when a component type is added. Highest-value genericity debt.

1. **Per-component inspector UI is fully hardcoded** ([inspector_panel.cpp:117](../src/editor/panels/inspector_panel.cpp#L117)). Adding a component means hand-writing a `drawXxxSection`, an add-menu entry, an `EntitySnapshot` field, a duplicate-entity line, a hierarchy tooltip entry, and an icon/name case — **6 places**. A single `ComponentDesc` registry `{name, accent, drawFn, snapshotFn, cloneFn, addFactory}` keyed by `typeId` collapses all six and makes new components automatically participate in undo/duplicate. **#1 genericity win.**
2. **`typeId<T>()` is one global counter shared by every registry** ([core/memory/types.h:65](../src/engine/core/memory/types.h#L65)). Components and resources draw IDs from the same sequence, so `Scene::m_components`, `ResourceManager::m_slots` and the event-bus vector are each sized to the *global* max type ID — sparse vectors full of null holes, and O(all-program-types) walks on entity destroy/clear. Give each registry family its own ID domain (`TypeIdGen<ComponentDomain>` etc.).
3. **`ISparseSet` can't copy an element generically** ([sparse_set.h:17](../src/engine/core/memory/sparse_set.h#L17)) — so the "generic entity cloning" claimed in notes **doesn't actually exist** (no `Scene::cloneEntity` in the tree). Add `virtual void copyElement(srcKey, dstKey, ISparseSet&)` and a `Scene::cloneEntity` that walks `m_components`.
4. **Enum ⇄ string tables hand-maintained in parallel**: `AssetKind` (3 edit sites, [asset_database.cpp:14](../src/engine/resource/asset_database.cpp#L14)), serializer enums (`LightType`/`ProjectionType`/`RenderMode`), and easing functions (31 functions across **three** parallel lists, [easing.h:137](../src/engine/system/animation/easing.h#L137)). Each wants a single `{value, name}` table driving all accessors. A `VKM_REFLECT_ENUM` macro would also let `Light`/`Mesh`/`Animation` rejoin the reflected-serialization path they bypass.
5. **Animation is hardcoded to Transform's pos/rot/scale** ([animation.h:19](../src/engine/ecs/component/animation.h#L19)) — can't animate light intensity, FOV, or material params. The generic `AnimationTrack<T>` already exists; the missing piece is a reflection-driven property binding (target component + field), backable by the existing `reflect.h`.
6. **Copy-paste load loops**: three structurally identical per-type asset-load loops ([asset_serializer.cpp:368](../src/engine/io/asset_serializer.cpp#L368)) and ~7 repeated texture-slot blocks in the folder loader ([material_loaders.cpp:126](../src/tools/loader/material_loaders.cpp#L126)). Collapsible with a template/table; low priority (leaf code).

Keep as-is: `AssetFactories` is a genuine `kind`-keyed generic registry with correct engine/tools layering — the model to follow.

## Q2 — Architectural issues

### Real bugs

- **`Resource` copy ctor/assignment silently drop `assetId`** ([resource.cpp:14-30](../src/engine/resource/resource.cpp#L14-L30)). Any value-copy of an asset resets its on-disk GUID to the invalid sentinel. Latent; the load-path `reconcileId` papers over it. One-line fix per member.
- **`RuntimeSettingsOverlay` (F10) edits the wrong source of truth.** [render_system.cpp:74](../src/engine/system/render/render_system.cpp#L74) overwrites `m_environment` from the scene's `EnvironmentConfig` every frame, but [runtime_settings_overlay.cpp:39](../src/editor/overlays/runtime_settings_overlay.cpp#L39) edits that mirror directly — so bloom/exposure/shadow sliders are silently reverted next frame. It must edit the scene component like other panels.
- **Inspector field edits bypass the undo stack entirely** ([inspector_panel.cpp:182](../src/editor/panels/inspector_panel.cpp#L182)). Only gizmo drags and add/remove-component push commands. Ctrl+Z can't undo typing a light intensity, FOV, or material value. The `tryMerge` coalescing machinery exists but is only wired to the gizmo. Route field edits through a generic `ComponentEditCommand<T>`.

### Design concerns (not bugs)

- **Generation counter is 31-bit and wraps silently** ([types.h:38](../src/engine/core/memory/types.h#L38)) — ABA after 2³¹ reuses of one slot. Retire slots on overflow or widen the field.
- **`Engine::run()` special-cases `RenderSystem` via `dynamic_cast` and requires exactly one** ([engine.cpp:102](../src/engine/core/engine.cpp#L102)) — makes the advertised "headless" mode impossible. A capability interface would decouple it.
- **Render pipeline depth is effectively 1** — `RenderThread` holds a single in-flight job; deepen to a 2-3 frame ring once the Tier-0 stalls are gone.
- **`ctx.deltaTime` is a stale 60-frame average**, read before the frame runs ([engine.cpp:35](../src/engine/core/engine.cpp#L35)). Feed raw previous-frame delta; keep the average for the FPS overlay only.
- **No spatial acceleration in culling** (no BVH/octree) — fine now, the eventual ceiling for large scenes. Per-test math is well-tuned.
- **Event subscriber lifetime is manual** ([event_system.h:61](../src/engine/system/event/event_system.h#L61)) — a captured-`this` handler whose owner dies without unsubscribing is dangling-handler UB. Return an RAII subscription token.
- **No backend factory despite the "backend-neutral API"** — selection is a hardcoded `make_unique<GLBackend>()`; `RenderBackendType::Optix/CPU` enum members advertise backends that don't exist. The interface is clean; the wiring isn't there.

## Q4 — File organization

**Verdict: leave it largely alone — one deletion + two micro-moves. The tree maps 1:1 to the CMake target graph; that is worth preserving.** The recent decomposition succeeded: `editor_system.cpp` is genuinely thin, the `framework/panels/overlays/gizmo/ui/input` split is coherent, and the `app/` (executables) vs `engine_app/` (shared bootstrap lib) + `VKM_WITH_EDITOR` design is excellent. `engine/system/` is *not* over-fragmented.

Concrete changes worth making:

1. **Delete `src/backend/{cpu_rtx,optix,vulkan}/`.** Empty, and since git can't track empty dirs they don't survive a clone — pure local clutter advertising backends that don't exist. Recreate when a real second backend starts.
2. **Move `runtime_settings_overlay`** out of `overlays/` — it's a floating F10 window, not a viewport-rect overlay. Belongs in `panels/` or a new `windows/`.
3. **`environment_inspector`** (733 lines, largest editor file) lives in `panels/` but is an *embeddable body*, not a docked panel — rename or move to `panels/inspectors/`.

Cosmetic-only (probably not worth the include churn): `engine/io/` (serialization) vs `engine/system/io/` (the file-watcher system) is a confusing name collision; renaming the former to `engine/serialization/` would clarify.

## Recommended order of work

1. **Tier 0 (an afternoon, mostly deletions):** profiler off + re-measure → remove `GLHiZPass` → defer the exposure readback. Re-measure after each. Expected to move FPS well past 300.
2. **Tier 1:** `parallelFor` fast-path + scene-unchanged short-circuit + batcher change-detection.
3. **Then pick an axis:** Tier 2 for high-res max-settings headroom; the `ComponentDesc` registry + inspector-undo for editor velocity and correctness.
4. The three real bugs (asset-id copy, F10 settings mirror, inspector undo) are independent — fix whenever.

## Appendix — what is already good (don't "fix")

- Render graph is compiled once and cached; not rebuilt per frame ([render_graph.cpp:239](../src/engine/system/render/render_graph.cpp#L239)).
- GL state changes are deduped via `Core::Context`; UBOs are `memcmp`-gated; uniform locations are cached; instancing/batching is real.
- Double-buffered `RenderView` + dedicated render thread overlaps CPU build with GPU execute.
- Transforms are dirty-flagged; camera entity is cached; visibility results reuse persistent buffers.
- Engine has zero GL leakage; editor↔backend goes entirely through abstract `RenderBackend`/`RenderTarget`; the pass downcast to `GLBackend` is legitimate (passes are backend code).
- `AssetFactories` registry + correct engine/tools layering; transactional scene+resource load (staging-then-swap); the `SparseSet`/`Handle<T>` family; the gizmo 4-file split; change-detected `MaterialPreviewSession`.
